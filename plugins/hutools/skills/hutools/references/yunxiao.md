# 云效问题单分析

## 接入指定项目

1. 从当前请求取项目网址，缺少时请用户填写。通过宿主浏览器打开用户指定的云效项目，优先复用已有登录会话。需要扫码时让用户看到云效官方登录页的实际二维码，等用户完成身份验证后重新读取项目页。若使用已连接的云效接口，通过连接器提供的只读查询识别账号及项目。采用接口前核对其是否支持附件下载、真实账号提及和评论回读，能力不足时可使用当前项目网页。以当次页面或连接器实际提供的操作为准。
2. 正式取单前，使用当前账号可见的授权信息，一次核对读取问题单和评论、下载附件、发表评论、@ 提单人所需的权限。使用确实需要令牌的接口时，通过凭据入口核对配置状态、可查的有效期和范围。预检只读。单据或附件特有的权限，标记为首次实际操作时核实。将已知缺项、当前官方页面中的入口、谁执行哪步及完成标志一次告诉用户。
3. 用户需要令牌时，引导其在官方授权页面配置，并通过连接器或宿主的受保护入口提供。令牌原文、登录二维码、带签名的下载地址仅在对应的交互中使用。管理员申请应能直接转交，例如“请为账号〈当前账号〉在〈实际项目〉开通〈实际缺少的操作〉，完成后我将通过〈受阻步骤〉核验”。HuTools 可代办的变更，先展示目标项目、操作和权限范围，收到明确同意后再执行。扫码、身份验证和管理员审批由相应人员完成。
4. 确认项目可访问后，向用户取得问题单号和本地父目录，沿用本次已给出的值。若宿主缺少可用的浏览器会话或连接器，说明需要接入的能力。网页不可达、会话失效、权限不足、无法访问指定单号时，立即在对话说明失败的步骤、目标及具体修正办法。网络和下载权限问题由账号或接入方解决。权限恢复后重试原步骤，保存已经完成的本地工作。

## 核对本地与云效材料

用包内[云效单据工具](../../../tools/yunxiao_issue.py)处理本地文件。下列命令从当前已加载的插件根目录执行，传入已确认的现有父目录和单号。将页面字段和路径作为独立参数传入。先运行盘点，它会创建或复用单号目录，列出普通文件的相对路径和字节数。

```sh
python3 tools/yunxiao_issue.py inspect --parent "$parent" --issue "$issue"
```

打开其中的历史报告、原始日志、bag、地图 JSON 等相关材料，标出已有故障时间、版本、证据位置和待核问题。随后确认并实际读取本次源码路径，核对版本。找不到源码或无法读取时，立即给出已检查的路径，请用户更正，收到答复后继续。

在刚确认的项目内按单号打开当前问题单，核对页面所属项目和单号，读取正文、提单人账号、评论和附件清单，翻页或展开直至覆盖与本次分析有关的内容。将提单人和经办人区分开。同名账号用云效资料页或提供的成员标识核实。若同号目录属于另一项目，请用户指定正确父目录，保护两单原件。

逐项核对已有材料所属的项目、单号、故障时段、源码或数据版本，以及文件能否读到覆盖该事件的记录。历史报告只提供线索，沿其引用复核原证据后才能采用结论。记录稳定的单据、评论或附件标识、版本或可用的校验信息及对应本地相对路径。可复用的直接读取，材料足够时，下载次数应为零。只有本次判断所需的缺件、损坏件或已更新件才从当前单据下载。用不同本地文件名保留同名的旧版与新版，查验下载产物，避免把登录页或失败响应当附件。附件拒绝访问时指出具体附件与受阻权限。

云效能提供稳定的项目、附件及可核验的修订标识时，下载前用 `lookup` 查询先前保存的副本。未找到时仍先核对盘点中的手工留存材料。确实需要下载时，使用当前网页或连接器将附件完整保存到新的临时位置，核实内容后调用 `store`，在报告中引用其实际返回的位置。

```sh
python3 tools/yunxiao_issue.py lookup --parent "$parent" --issue "$issue" \
  --project "$project" --attachment "$attachment" --revision "$revision"
python3 tools/yunxiao_issue.py store --parent "$parent" --issue "$issue" \
  --project "$project" --attachment "$attachment" --revision "$revision" \
  --file "$downloaded_file" --name "$attachment_name"
```

若没有可核验的修订标识，回到原单，以已知的来源、时段、版本和实际内容判断。确需补件时下载到本单内未占用的位置并记录来源，把未知的修订标为待核。

## 判断与归档

收集结束后直接判断。**能定位与故障对应的时间，且能读到同一事件的相关日志**，才进行根因分析。时间可来自现场标记、材料间可核对的事件或问题单描述，记录时区或时钟关系。建单时间和孤立的普通日志时间戳不足以定位故障。

- 能定位异常就分析，即使原描述模糊。报告先用一句话写触发条件、实际行为和结果，随后引用时间、观测值、日志文件及行号或记录位置，结合源码版本和位置串起事件。已定位的环节直接给结论。仅有线索时说明首要解释、支持它的观测，以及需要哪个时段、哪个模块的哪项记录和什么结果才能确认或修正判断。辅助 bag 或地图缺失时写清影响。
- 缺故障时间或可读的相关日志时，停止归因。两者都缺时一次列全。材料齐备仍无法区分目标事件时，围绕已读材料给可作答的描述示例。例如日志显示两次停车，就请提单人指明哪一次和当时预期动作。其他阻断项也只索取足以恢复分析的最少数据。

在报告的「问题根因」下记录结论或已核实事实、关键时间线与证据引用，在「解决方案」下写明拟改位置、预期效果和验证方法，或继续调查所需材料及判据。保留本单来源、适用版本、本地相对路径和证据位置。按下节起草评论，在报告末尾单列「评论草稿」，记下目标项目、单号、提单人账号、待确认状态，并原样保存完整评论正文。将报告的 UTF-8 正文通过标准输入交给 `report`，例如从本次起草的临时文件读取。该命令保存至本单目录的 `详细分析报告.md`，内容有变更时保留历史报告。实际打开返回的文件核对后再展示草稿。

```sh
python3 tools/yunxiao_issue.py report --parent "$parent" --issue "$issue" < "$draft_file"
```

## 审阅和发布评论

本地报告保存后，在当前对话展示可打开的报告路径、目标项目和问题单号、将被 @ 的实际提单人及**完整评论原文**。评论面向提单人，日志引用用其可定位的文件名、时刻或记录号。

- 能分析时以「问题根因」「解决方案」两部分起草。第一句给判断，随后用关键时间、观测和位置支持结论。「解决方案」给具体动作和验证判据。
- 分析受阻时以“请提供缺少的关键数据”提出已核实的实际缺项、所需范围及补齐后可核对的判断。用户的访问权限问题留在对话处理。
- 两类草稿都以“谁接下来做什么”收尾。需要协作时写出谁先补哪项数据、随后由哪个已知模块核对什么。能分析的评论把这句话放在「解决方案」末尾。

用宿主可用的选项卡让用户选择发布当前完整稿、修改或保留草稿。收到修改意见后，用 `report` 保存新稿和待确认状态，重新展示单号、提单人和完整改稿，再取确认。用户取消、尚未答复或会话中断，均保留草稿。确认仅适用于展示的项目、单号、账号对象和原文。恢复时对照本地草稿和对话中的明确答复，无法核对答复时，重新展示原稿供用户决定。

收到明确发布确认后，在同一单据编辑器中输入已确认内容，用云效的 @ 成员选择器选中该账号。连接器提供结构化提及时可按成员标识设置。提交前核对单号、正文和实际提及对象，无法唯一匹配或无法形成有效提及时暂停并说明。在报告的草稿状态中记录本次提交的账号、时间和“发布待核实”，保存后提交一次。再从该单评论区回读新增评论，核对原文和可打开的成员提及，记录评论标识或定位链接。回读一致后将状态更新为“已发布”并告知用户。

提交超时、页面跳转异常或中断后恢复时，先刷新并查询已有评论，按作者、正文、提及和发布时间查找本次提交。找到即核实并记录。仍无法判定是否成功时保留“发布待核实”，告知用户状态，停止再次发送。若已明确服务端拒绝写入，说明真实受阻原因，恢复后再次查该单评论区、核对原稿和确认范围，再处理已知失败的提交。
