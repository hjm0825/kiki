# 问题分析

用户在启动卡片选择「分析问题」或直接指定云效项目、问题单时，进入[云效问题单分析](yunxiao.md)，先接收本次项目网址，收到后立即预检。用户已经明确要分析本地源码、日志或其他非云效材料时，直接按下面的流程处理。

## 本地问题分析

只补齐影响分析的信息：源码/材料位置、实际与预期现象、发生时间/时区或触发条件。用户已给完整输入就开始，不重复问模式。先核对版本、日志日期与时钟基准；没有精确时间时从事件或最小场景定位。

1. 围绕现象阅读相关实现、调用方、配置和日志。区分环境、接口、算法、运行和部署问题。引用文件行或记录标识；不要仅凭相邻报错认定因果。
2. 列有证据支持的候选原因和可区分它们的观察。优先验证最可能且低成本的解释，不为凑数制造假设。按需使用 [diagnosing-bugs](../../diagnosing-bugs/SKILL.md)。
3. 用适用的只读检查、已有安全测试或输入重放核实；执行前读清脚本副作用，遵守[共同规则](rules.md)。无法接触现场时从已有资料推断并明确首要判断，给用户最小补证操作。
4. 提出首选解决方案：为什么改、改哪里、前后行为、接口/依赖/部署影响、如何验证及恢复。分析本身不授权修改产品。
5. 按[报告模板](../assets/problem-report.md)写入已有问题目录，同步上级索引并给用户链接。输入目录只读；输入身份与范围写入报告，不复制整套日志。

报告要给倾向和行动。根因定位需要决定性证据；未定位时写最可能原因、支持/反对证据以及下一步最小辨别手段。不要写无依据的置信百分比，也不要把“方案提出”标成“问题已修复”。

收尾核对本次工作、未提交用户改动、原始输入、报告链接与必要证据；按规则处理本批文档提交。复杂问题按需启用独立只读审查，让其直接看原材料和结论，不只接受作者解释。
