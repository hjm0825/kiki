## R2-Q6：规则的承载方式（第三轮细化后于 2026-11-17 确认）
推荐短 AGENTS.md 保留共同底线、规则优先级及导航；角色工作手册承载职责细节；项目契约保留项目事实；能稳定判断的规则进入权限控制或可执行检查。共同底线有唯一来源，各角色引用，避免五份副本漂移。每项迁移保留旧条款→新归属→责任角色→执行/复核方式的映射，删并条款说明理由；不以减少字数为验收。

| 原规则价值 | 主要责任（建议） | 可检查的部分与判断边界 |
| --- | --- | --- |
| 需求、调研、确认边界、兼容及取舍（§2、4、5） | 经理 | 授权范围与版本可以校验；方案是否适合工程仍须判断 |
| 修改前调查、变更记录、可迁移实现、恢复（§3.1、4、5） | 开发 | 写入范围、差异、部分依赖与路径规则可检查；设计是否正确不能仅靠检查器 |
| 测试真实性、需求证据、失败/边界/恢复、独立审查（§1、6） | 测试与独立审查 | 可验证执行结果及被测版本；测试是否覆盖真实需求仍需审查 |
| 文档、索引、原始事实、归档、精确处置（§3、7、8） | 资料管理 | 引用/校验/受保护路径可检查；唯一性与保留价值需要来源和依赖证据 |
| 停止条件、阶段状态、资源、阻塞、改进（§1、2、8、9及旧稿§9） | 协作观察，经理负责调度 | 可记录可观察事件和超预算；长耗时不自动等于无效，不可观测数据不编造 |

所有角色共同遵守资产保护、事实真实性、授权边界、禁止改判据制造通过。上表是迁移方向，尚非逐条审计或已实现的隔离机制。

## R2-Q7：严格约束的含义与失效处理（2026-11-17 已确认）
用户确认在接入的受控执行范围内分三类落实：越权写入/受保护资产/未授权删除等尽量在操作前阻止；必要验收证据缺失或检查失败时禁止标记验收完成；研究深度、设计质量等通过角色责任和独立审查控制。必须区分“事前阻止”“交付检查”“事后发现”“仅文字约定”。关键保护无法生效时，停止对应高风险动作并说明缺口，独立只读调查可继续；不默认降级后宣称严格受控。

该决定不保证所有工具都有可拦截入口，也不把工程测试通过解释为绝无缺陷。是否新增运行组件及其成本，需在实际能力核验后另定。

| 类别 | 默认归属 | 已确认的通用退出/处置条件 |

每工程开始生成数据前确定：精确目录/类别、容量边界、保留截止日期或可核验事件、恢复条件、可执行的动作。涉及持续处置授权的具体范围由用户确认，已覆盖的执行无需逐批重复询问。未设置或无法核实的条目不能自动清理；到期只是触发审查。每次执行生成精确清单、核对真实路径及跨工作区依赖、保留轻量处置记录；归档不自动授予外部唯一原件永久删除权。

授权差别须明确：现有 AGENTS.md §8.3 写明“规则确认不授权未来所有删除”。用户本轮已确认通用规则 V0：仅对用户批准的具体项目目录、类别、条件和动作授予持续授权，满足条件的清单可按规则执行；未覆盖项仍需单独确认。当前没有指定本机处置对象，不执行删除。保留时长/容量按项目需求确定，不在通用规则中硬设天数或大小。

## R2-Q9：规则的版本与变更权（2026-11-17 已确认）
用户同意：项目明确采用一个已确认的团队规则版本；协作观察角色根据数据提出改进，变更在独立试行与复核后由用户批准采用。执行中的 agent 不得为当前任务通过而修改自身权限、验收门槛或处置条件；通用规则升级不静默覆盖所有工程，避免同一任务中途规则漂移。具体载体和分发方式后续确定。“可以批准”记录为接受上述批准机制，不解释为已经批准未知的未来规则改动。

## 已确认：内外层资料与主线
用户明确要求：整个资料管理分为外层与内层。外层用于给用户汇报，简洁、清晰、突出重点，覆盖设计方案、测试报告、修改点记录、阶段实施方案等；内层供团队使用，可以详细深入，但必须有条理、能闭环、不杂乱。流程以需求、设计、开发、测试为主线；团队根据不同项目灵活制定项目约定，底层规则不变。

落实到本轮文档：先增设对外摘要，详细记录继续沿用本文；不立即搬动工程其他文档或建立新目录。以下为写作应用方式，不另加硬性页数/字数门槛：

| 文档类型 | 外层优先回答 | 内层保留 |
| --- | --- | --- |
| 需求/设计方案 | 解决什么、推荐什么、收益与代价、需要用户决定什么 | 原始需求、调研与源码依据、备选取舍、接口/部署影响、未决假设 |
| 阶段实施方案 | 本批目标、范围、完成标志、主要风险 | 任务依赖、角色交接、授权范围、版本和验证/恢复办法 |
| 修改记录 | 改了什么、为什么、前后行为、是否解决问题 | 文件/函数差异、来源、实施经过与证据 |
| 测试报告 | 哪些需求通过/失败/待验、影响与交付建议 | 被测版本、环境、输入、命令、原始结果、失败与重验历史 |

外层不隐藏核心缺陷、不把未验证写成通过。内层以需求、任务、版本和证据关联组织，保留必要完整集合，不等于永久保存全部过程数据。内外层是阅读与职责划分；工程/资料库是保存位置划分：内层小型必要资料仍可留工程，大型原始资料按 Q8 外置。任何一层都不能成为另一套独立事实台账。

## Q6 细化方案（2026-11-17 已确认）
采用共同底线与导航、角色细则、项目约定、可执行检查四类承载；底层原则稳定。团队自行查明并记录已有目录、构建/测试入口等事实；在已批准方案内自主安排任务粒度、报告组织、执行次序等细节，不逐项要求用户决定。技术栈/依赖、公共接口、部署方式、验收要求、权限和数据处置范围等实质变化按已有确认边界处理。不能因称为“项目约定”就静默放宽底层规则，也不把未知事实自行写成已确认事实。项目特例与已批准底线冲突时说明影响，交用户决定。

## Q10：主线如何推进（2026-11-17 已确认）
用户确认先建立整体目标与必要架构认识，再按可独立验收的功能分批走通需求→设计→开发→测试。需求阶段即定义验收实例，开发阶段持续单测，集成与端到端在适当阶段验证；四阶段是工作主线，不表示测试只在开发结束后出现。跨模块功能以真实用户链路完成为批次完成依据，不能用各模块分别通过替代整合验收。批次粒度由经理根据依赖和风险调整，不要求所有项目同一时长或规模。

## Q11：测试与开发争议如何裁决（2026-11-17 已确认）
用户确认测试角色可依据明确需求与证据阻止验收完成，并说明影响和复现方法；开发提交修复及其证据，不能单方面改验收实例/降低判据解除失败。测试本身可能错误，经理对照需求和原始证据裁决；已确认范围内修正错误测试并复核，不把任意测试失败当成永久否决。涉及需求歧义、验收变化或风险接受时交用户决定；必要独立审查沿用 D09，不将角色名称视为隔离证明。核心缺陷未解决不能仅因进度压力标记通过。

## Q12：跨电脑与工程复用的可验收边界（2026-11-17 已确认）
用户确认交付可携带、可定位版本的团队规则/角色/必要检查与恢复说明，项目内容独立；新机器通过接入检查识别运行环境、权限与必要工具，新工程通过调查形成项目约定，无需用户手工重写整套规则。不依赖当前聊天、机器绝对路径或原工程安装产物；账号/密钥重新配置，不随包复制。跨系统复用作为设计目标，具体系统和运行环境的支持按验证结果声明；第一版沿用 D01 的 Codex 范围，不隐含所有 agent 平台均已适配。

恢复验收建议包含：在没有原目录和旧会话的独立环境中加载规则、接入示例工程、执行一次必要检查并恢复任务状态；仅复制 Markdown 文件不等于验证通过。可用环境与跨机器实测方式在实施前确定；不能访问第二台机器时如实记录尚未实测。

## Q13：对现有部署的默认策略（2026-11-17 已确认并补充）

## 新增共同要求（用户明确提出，2026-11-17）
- **实事求是、用数据说话。** 结论追溯来源、版本和必要测量口径；区分源码事实、历史记录、实测、推断与未知项。没有数据就标明缺口，不把“用数据”变成编造评分、阈值或收益。

## R9-Q19：每项功能的系统影响检查（2026-11-17 用户同意）

1. 行为和状态属于哪个模块，谁拥有数据与副作用，是否出现重复职责。
2. 与哪些生产者/消费者交互，接口语义和允许的依赖方向是什么。
3. 是否增加源码、构建、安装或运行依赖；目标部署能否单独保留、更新或移除相关模块。
4. 已批准的旧组合如何继续工作，哪些组合必须验证，失败如何恢复。

小改写简短影响结论，跨模块、公共接口或部署变化再补依赖图和组合清单。功能边界应与实际独立变化、测试和部署需求相称，不默认每功能一个包/进程，不为假想需求建立通用框架。

对仿真案例，建议约束为：业务核心通过明确接口与环境交互，仿真专属转换/注入/观测留在适配边界；公共接口和公共能力有独立职责，不能让核心通过公共包间接依赖整套仿真。核心算法、安全和故障语义不能为“解耦”挪进适配层或关闭。结合依赖检查，在缺少仿真开发环境的目标组合中验证独立构建和消费；现场运行仍由用户验证。

存量边界不合理时记录实际影响与修订方案，由用户决定治理批次；新增功能不应默默扩大已有耦合。尚未批准当前工程重构或新的依赖门槛。

## R10-Q20：代码与面向人阅读材料的可读性规范 V0（2026-11-17 已确认）
| 方面 | 已确认约定 | 审查时看什么 |
| --- | --- | --- |
| 命名 | 标识符沿用语言和项目惯例，优先明确的英文领域词；同概念同名称，避免随意缩写和万能 Manager/Utils | 看调用处能否理解操作及数据意义，重要单位/坐标系是否清楚 |

| 封装 | 公共接口表达调用者需要的能力，内部表示与实现细节留在模块内；抽象服务于已知变化或清楚边界 | 调用者能只读接口完成使用；不会绕过接口改内部状态；不为想象中的复用堆继承和包装 |

参考成熟规范中的可读性方法：[Google C++ 注释章节](https://google.github.io/styleguide/cppguide.html#Comments)强调有价值的接口/实现说明；[C++ Core Guidelines 的 C.2/C.4 与 NL.1～3](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)讨论类/函数选择及简洁意图注释；[PEP 257](https://peps.python.org/pep-0257/)给出模块、类、函数说明的结构。格式、部分命名与说明是否存在可以自动检查；含义是否清楚由审查者指出具体代码和阅读困难，不能用主观“还不够优雅”无限打回。

## R10-Q23：明确推荐并承担判断责任（2026-11-17 已确认）
面向用户的决策答复先说推荐或反对什么，再给决定性理由和行动；有真正不同的可行取舍才列备选。确实缺关键事实时，推荐一个最小补证动作，并说明拿到什么结果会改变选择。员工可以有证据地反对用户的初始想法。

外层只报告会改变当前决定、使用条件、风险或下一步的未知项；说明具体影响与处理办法。其余测试范围和来源细节留内层可追溯记录。同一状态不反复附“仅供参考、不能证明、不能保证”等泛化免责声明；实际失败、关键未验项和反证必须直说，不用自信语气替代证据。

表达示例（假设案例）：把“研究不能证明方案有效，仍需进一步验证”改为“建议采用 A：现有工具链可支持，改动集中在适配层。B 需要升级公共依赖，当前收益不足。A 的现场驱动版本尚待采集，先完成独立逻辑和本机集成，部署前核对该版本。”如果缺的是决定接口的关键事实，应先推荐核实它，而非继续依赖猜测实施。

## R10-Q24：按实际影响决定测试投入与停止（2026-11-17 已确认）
测试启动前，在现有计划记录目标需求/风险、失败的实际后果、检查组合、完成条件及投入上限。轻量验证可合并成一行，必要测试不逐条让用户确认。分类与动作如下：

| 类别 | 典型情形 | 处理 |
| --- | --- | --- |
| 必须解决或完成验证 | 核心功能错误、确实违反已确认硬门、实际安全/数据/恢复风险 | 阻塞相关交付；达到预算先诊断和重排，不能因到时变成通过 |
| 普通缺陷或目标偏差 | 影响局部体验或性能，但不违反硬性要求 | 经理按实际影响给出本批修复或后续处理建议，在授权范围内取舍 |
| 观察项 | 没有对应明确性能需求、功能损害或实质风险证据的轻微波动 | 做有界有效性核查，必要验证完成即交付，记录后续触发条件 |

对低影响观察项，首版试行默认一轮有限核查，测量条件有明确问题时最多增加一次复测；累计额外排查以 15 分钟为初始复查上限。此值是试行投入参数，不是质量阈值，不适用于计划内构建、已要求的稳定性测试或核心故障；项目可在开始前按实际需求设定相称预算。若最小有效检查本就需更久，经理先说明实际价值，决定是否纳入计划，而非启动无效短测。

时间按同一问题累计，换 agent、工具或方法不清零。达到停止条件、无新证据或预算到点即停止额外排查；续查须记录新证据、可能改变的交付判断、预期收益和新的停止点。观察员发现无依据续跑时暂停该项并通知经理；经理在已有授权/预算内处理，只有扩大范围或改变验收等需要用户决定。

数毫秒例子：普通仿真显示的轻微抖动，若有限核查未发现影响结果、交互要求或时序正确性，记观察项后交付；若同样差异造成控制周期超时或消息丢失，则按实际后果处理。禁止为消除随机波动、改善统计外观而反复跑数小时；已确认的性能硬门按既有变更规则处理。

## R10-Q25：先调查再建议，并用动作检验原则（2026-11-17 已确认）
正式拆解实施需求或推荐技术方案前，经理先回答本次决定依赖哪些事实，再取得必要依据。需求澄清和列未知项可在调查前进行；未经调查的候选只用于形成问题，不包装成正式推荐。

调查包含项目已有需求、代码、配置、部署和历史证据；涉及行业方案或新技术选型时查相应版本的原始资料。已有证据仍适用则复用并核对，不为形式重新全仓扫描或每次上网。仅网站数量、链接数量和调用 research 技能不能作为调查完成条件。选择已批准方案范围内的普通实现细节，按受影响代码和已有依据处理。

经理在现有任务/设计记录中留下短依据：当前要决定什么→已查的本地能力与外部依据→关键结论→推荐及取舍理由→会改变决定的未知项及处理。没有足够关键依据就先做最小补查；非关键未知不阻止给有倾向的建议。调查停止点是足以回答当前决策，不是穷尽所有资料。

| 原则 | 触发时的动作 | 负责人/如何核验 |
| --- | --- | --- |
| 先调研再建议 | 推荐前核对相关本地事实；行业选型取得适用原始来源 | 经理执行，审查者核对关键依据实际支持结论；缺关键依据退回补查 |
| 实事求是、用数据说话 | 关键结论有来源；关键数值有版本、环境和口径；推断与实测分开 | 执行角色留证，测试/审查核对结论到原始结果；不为定性取舍编造评分 |
| less is more | 新增类、接口、组件、依赖、流程或文档时说明解决的具体问题，以及为何现有能力不够 | 开发/经理提出最小完整方案；审查无收益包装和重复事实源；不设代码行数或文件数 KPI |
| 系统思考、模块化 | 修改前执行已确认 Q19 四项影响检查 | 经理/开发负责，审查结合实际调用与构建/部署依赖核对 |
| 及时交付、测试适度 | 每项必要验证映射需求/风险；按问题累计投入并执行 Q24 停止条件 | 测试执行，观察员发现无新证据重复，经理关闭非关键排查 |

每条核心规则进入试行时配至少一个“违反规则的样例→应有处理”：无来源就推荐、没有需求依据的性能硬门、仅为包装普通函数建空类、引用旧版本测试作本版结论、重复测试无新证据。结构字段用检查器核对；来源是否充分、抽象是否必要等由审查者给出具体判断。共用已有记录，不增加平行台账。

| 模式 | 经理的入口行为 | 后续动作与交付 |
| --- | --- | --- |
| 开发 | 识别当前工程，询问要解决的问题、使用者和预期结果；读取已有约定与实现 | 需求讨论与针对性调研→系统设计和验收实例→用户确认修改批次→按需研发/测试→简明修改报告与本批本地 Git 提交 |
| 分析问题 | 优先读取已知入口，仅补问缺少的源码/资料位置、实际与预期现象、发生时间或触发条件 | 核对输入身份和时间线→追踪源码及日志→验证候选原因→提出首选解决方案→输出 `.md` 报告与必要证据索引 |
| 其他 | 直接理解问题，按需调查、讨论或解释 | 默认对话回答；需要文件或行动时按目标进入相应流程，避免简单咨询启动全套团队 |

分析入场问题按三个信息组组织：①源码和分析材料位置；②实际现象与预期表现；③发生时间、时区或可定位的触发条件。已给或可直接读取的内容不重复询问；没有准确时间时可从日志或复现条件继续缩小范围。报告输出沿项目已有问题目录和索引，未约定时在接入中明确；外部项目保持自身归属。

分析模式默认只读源码/原始材料，可在约定报告目录写分析成果。依现有授权执行安全只读调查和有限验证；需要修改源码、插入探针或改变环境时，提出具体方案进入原有确认流程。输出方案本身不触发自动修复。

## 问题报告最小结构（建议）
同一 Markdown 报告先给用户结论，再按需展开依据：

1. **结论摘要**：问题、实际影响、当前判断及推荐动作。
2. **问题根因**：原因与触发链；已定位则给决定性证据，未完全定位则给首要判断、反证与最小补证办法。
3. **解决方案**：首选方案、涉及模块、修改前后行为、兼容影响；确有不同取舍再列备选。
4. **验证办法**：如何复现、如何判断修复、必要回归和停止条件。
5. **证据与输入**：源码版本、材料身份、现象时间线和证据定位，避免粘贴大量原始日志。
6. **状态与下一步**：分析完成、修复方案待确认、已修复、已验证分别记录，供后续接续。

入口验收包含：新安装后选择插件并发送“运行”得到引导；已明确目标不重复询问；分析只补问缺失输入并生成可追溯报告；简单咨询直接回答；恢复旧任务和切换工程时正确使用对应状态。权限、跨机器和员工分工仍沿已确认试行要求验证。

## 中途选择与填写卡片
用户要求引导发生在处理过程中，以可填写的独立卡片呈现，填写后继续处理，避免每次结束答复后再要求用户逐条发送“同意”。此项作为 HuTools 入口和需求访谈的交互要求。

1. 首版优先复用宿主现成的异步提问能力。当前会话已实际调用该能力收集公开方式并收到用户答复；无需为此搭建独立网页或服务。
2. 模式选择用短选项；源码/资料路径、现象和时间用文字输入，每轮通常 1～3 个相关问题，已有信息不重复索取。路径可粘贴；文件附件通过宿主原有附件入口提供，不把文字卡片当文件上传控件。
3. 等待时可以读取已知工程材料、检查已有约定等无依赖工作；必需输入未返回前，依赖该输入的动作保持等待。答复到达即合并上下文并继续，不要求用户再输入“继续”。
4. 用户已确认的范围内正常推进。遇到新的实质方案选择或必须确认的修改批次，先给具体摘要和详细记录入口，再用宿主允许的明确确认方式收集决定；预选、取消、超时和未回复均不算同意。
5. 中断后从任务记录恢复已确认信息及未答问题，避免重复提交任务或丢失输入；关键回答随节点落入既有记录。
6. 安装验收检查实际目标客户端能否呈现和回传卡片。宿主缺少该入口时明确标为交互能力缺口，并提供简短文字问答作为临时路径；不把能调用普通工具当作卡片接续已验证。

官方 [Codex App Server 用户输入协议](https://learn.chatgpt.com/docs/app-server#toolrequestuserinput)提供处理中提问与答复事件；本轮方案优先使用宿主已暴露能力，不要求重建客户端，也不将协议存在直接等同于所有客户端支持相同样式。
